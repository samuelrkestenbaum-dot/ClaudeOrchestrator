## Gate 2 — what attachment actually does (measured on a genuinely fresh project)

A disposable project (`/tmp/freshproj`: `git init`, `app.js`, `README.md`, **no** `.claude/`,
**no** `build-os/`) was created and a **real, authenticated `claude` CLI session** was run with a
neutral prompt and **no installation instruction**. Baseline was clean: user-scope
`~/.claude/settings.json` had **no** hooks and `~/.claude/agents` was empty.

**Findings (all negative results are real and are reported as such):**
1. **Attachment alone installs nothing.** With ClaudeOrchestrator merely present alongside the
   fresh project, the session answered normally and the project received **no** `.claude/`,
   **no** `build-os/`, **no** manifest.
2. **`claude -p` does not run SessionStart hooks at all** — not project-scope, and not
   user-scope. Proven three ways: (a) after installing the project runtime, deleting a managed
   file and starting a fresh `-p` session did **not** restore it; (b) the same test inside
   **ClaudeOrchestrator itself** (control) also did not fire; (c) after running
   `install-global.sh` (user-scope hooks wired, confirmed in `~/.claude/settings.json`), a fresh
   `-p` session in the untrusted project still did **not** fire. Both projects show
   `hasTrustDialogAccepted: false`.
3. **SessionStart hooks DO run on the managed surfaces** (web / cloud task / interactive) — this
   session's own transcript carries `SessionStart … Orchestrator: ON`, which is how the hook fires
   in practice.

**Conclusion — the smallest supported activation is one command, then automatic:**
`bash /path/to/ClaudeOrchestrator/build-os/tools/project-bootstrap.sh` run once from the project.
Live proof in the fresh project: complete runtime installed; `Orchestrator: ON`;
**installed source SHA `e66f43e3af68` == canonical**; agents 5/5
(build-orchestrator, builder, qa, reviewer, archivist); tools present (specialist-handoff,
capability-profile, supervise, skill-budget-audit, project-bootstrap); a second run reported
**"already up to date … skipped, no files copied"** (idempotent cache hit); project-specific files
(`current_state.md`, `residue.md`, `active_packet.md`, `receipts/README.md`) reported preserved.
**No manual bootstrap command beyond that single activation, and no per-project instructions.**

We do **not** claim attachment-only installation — the live test refutes it.

## Defect found and fixed by this investigation

A **vendored** copy (installed into a project) has `SRC == TARGET`, so it has no canonical source
to copy from and cannot self-heal — yet it reported `bootstrap: source repo (no install needed)`
while simultaneously reporting `DEGRADED`. Fixed: an incomplete vendored copy now prints
`REPAIR: this is a vendored copy with no canonical source attached — it cannot self-heal.` plus the
exact command, and the hook's status line no longer says "no install needed". Verified live.
Tests §26-I3 (+3 checks): DEGRADED reported, self-heal inability stated, repair command named.
